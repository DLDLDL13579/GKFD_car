## 3. 下行中继原理（为何不用 domain_bridge）

- **domain_bridge 0.5.0 无法向"非默认域"发布**：主车域1 → robot1 域21 方向端点存在但零数据（实测 40 条发布零到达）；反向（21→1）正常。
- 因此下行走两个进程：`src`（域1，订阅主车调度话题）→ 本机 TCP(127.0.0.1:39211/39212) → `dst`（域21/域11，发布到次车域）。
- 消息协议：`4B 长度 + "topic|type|" + CDR 序列化字节`；断线自动重连。
- 修复记录：dst 的 `create_connection(timeout=2)` 使 recv 带超时，空闲被误判断线重连（会漏消息）——连接成功后必须 `settimeout(None)`。

### 7.1 一键切换（核心交付）


各分支自动完成四步（以 `rtab` 为例）：

1. **清旧栈** —— 组件进程（`component_container` / `map_server` / `amcl` / `rtabmap`）**和 launch 残留都要清**。只 kill launch 会留下容器子进程，导致两套 nav2 并存、新栈报 `Failed to change state for node: controller_server`
2. 起 `ros2 launch largemodel largemodel_nav.launch.py`（主线；备选为 `..._nav_amcl.launch.py`）
3. 校验（**两分支不同**）←订正2026-09-24：**amcl 分支**查 `Managed nodes are active` + 日志 `createLaserObject`（AMCL 收到激光）+ `Received a` 最后一条；**rtab 分支**只查 `Managed nodes are active` + 打印 `WM=` 行。两者都**不**校验地图尺寸（原述「校验三件事 / 打印地图 1380×910」与脚本实际不符）
4. **自动设发车点初始位姿**：`bash ~/set_start_pose.sh` —— 读 `~/maincar_start_pose.txt` 的 G 点后调 `sip_arg.py` **直接发送** `/initialpose`（**只发定位、无任何运动**）。←订正2026-09-24：原述「自动跑全局定位、并打印 `sip_arg.py` 命令」与脚本不符（全局匹配工具 `lgm.py` 是**人工**诊断命令，脚本不调用它）

⚠️ **两套互斥**（都会发布 `map→odom`），切换前必须停干净。

### 7.2 地图闭环（语音建图 → 导航栈直接用）←订正2026-09-20

```

   ⇒ 建图后须重跑一次 db 位姿变换，否则两车坐标立刻脱钩 ←订正2026-09-20
```

- **AMCL 版与 RTAB 版的默认地图都是 `my_map.yaml`**，共用同一份；RTAB 另需 `my_room.db`。←订正2026-09-20：**该 `my_map.*` 现为融合图**（狗图 + 本车观测取并集，1380×910 origin −12.812/−15.218，未知区 0%），并且 `my_room.db` 已变换到同一坐标系 —— **「同源」由「配准 + 位姿变换」保证，不再依赖「建图时一起保存」**
- ⚠️ **不要把默认地图改成别的文件名**（例如 `dog_map_20260910.yaml`）—— 那样语音建图存出的 `my_map.*` 永远喂不进导航栈

### 7.4 排障清单（2026-09-17 实车踩过）

| 现象 | 真因 | 处置 |
|---|---|---|
| Nav2 刷 `Extrapolation Error`，且 `Requested time` **固定不变** | **上游定位节点已死**（AMCL 崩溃 / rtabmap 未重定位），不是 TF 配置问题 | `grep -a "process has died" ~/nav_amcl*.log`；重启 nav2 栈。←订正2026-09-20：**RTAB 主线下更常见的是「车不在图覆盖区内 ⇒ rtabmap 报 (0,0) 定位不上」**，此时 `global_costmap` 会无限刷 `Timed out waiting for transform from base_footprint to map` |
| `/scan` 有 publisher 但收不到数据 | ① 雷达串口失效（USB 重新枚举后驱动捏着失效 fd）② QoS 不匹配 | `python3 ~/check_scan.py` 双 QoS 探针区分；串口失效则 `systemctl --user restart largemodel-control` |
| **所有**导航目标 `REJECTED` | 误删 `/dev/shm/fastrtps_*` **破坏 DDS**（症状：外部进程互通、外部↔容器内节点不通） | 重启 control 栈 + nav2 栈即可恢复（**不必重启整机**）；判据是 AMCL 日志重新出现 `createLaserObject` |
| 改了 launch 但行为没变 | **`install/` 是实体文件不是软链**，`ros2 launch` 读的是 install 版本 | `cp src/... install/...` **两份同步**（本项目 `system_manager` 也是同类问题） |
| 定位进程崩溃后没被自动拉起 | **`use_respawn` 只管容器进程、不管容器内的组件** | 需独立看门狗（见 §7.5）←订正2026-09-20 |
| **所有导航节点起来了但 `bt_navigator` 一直 inactive** | 定位初值离实际位置过远（实测偏 6.58 m）⇒ 不发 `map→odom` ⇒ costmap 等 TF 超时 | 用 `lgm.py` 重测当前位姿并写入 `initial_pose`；判据是日志出现 `lifecycle_manager_navigation: Managed nodes are active` ←新增2026-09-20 |
| 起栈报 `Failed to change state for node: controller_server` | 旧栈容器残留，两套 nav2 并存 | 按 §7.1 步骤 1 连组件一起清 |
| 控制栈启动后雷达/底盘节点缺失、`action_service` 刷"传感器数据异常" | **串口枚举比服务启动晚**（服务 `ExecStartPre` 只等麦克风不等串口） | `systemctl --user restart largemodel-control` |

**清理 `/dev/shm/fastrtps_*` 的正确姿势**（这是项目既有的处置手段，别因噎废食）：**必须在所有 ROS 进程停止时清理** —— 先停 control 栈与 nav2 栈 → 再删 → 再依次起 control、nav2。**运行中直接删会破坏 FastDDS 共享内存状态**，症状见上表「所有导航目标 REJECTED」行。←订正2026-09-17：此前记作"绝对不要删"，说法过于绝对；恰当规则是"**只在进程停止时删**"（既有文档记载的"清理残留锁"场景依然成立）。
